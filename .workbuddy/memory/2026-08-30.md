  → 从**不同阶段不同文档**提取**语义事实值**（API 路径/需求编号）与声明的 authority 比对，是**内容一致性**问题

## evoucher 插件重设计评估（用户问"是否重新设计插件以彻底重构 evoucher"）

产出：`dsh-plugin-doc-lens/docs/ADR-plugin-redesign-evaluation.md`

### 现场核实纠正了两处旧假设
- `extends: "evoucher"` **有效**（内置 profile 在 `profiles.ts:45`），非悬空；但造成**配置双源**（内置 profile + 本地 .doc-lensrc 都定义 stages/facts，本地整段遮蔽内置 → 内置改了本地静默漂移）。这才是"配置漂移"真根因。
- doc-lens **已构建**（`lib/` 存在，之前误查 `dist/` 判未构建）。

### 实测根因（三类漂移）
1. 配置漂移 = 配置双源（内置 profile vs 本地覆盖）
2. 代码-行为偏差 = ADR 方案 C 主张并入 docpath，实现却是独立 cordis 插件（事后更对，但 ADR 未更新）+ 测试盲区（2816 LOC 仅 `kernel.test.ts` 1 文件，cli/config/extract/scan/drift/adjudication 零单测）
3. 版本不一致 = 无独立 semver（随 monorepo 基线 v2.0.1）+ 硬 pin RC 预发布宿主（cordis@4.0.1 + dsh-client-*@0.1.0-rc.7 + dsh-tools@0.1.0-rc.7）

### 贯穿三者的母体
内核 `src/kernel/` 与宿主适配层（cordis/React/client.ts）**未物理分离** → 宿主变全包受影响、CI 无法单独跑内核、内核无法脱离宿主测。

### 推荐结论
**重构 + 扩展，不重写**。最高杠杆 = 内核/宿主拆层（doc-lens-core 纯 TS 无宿主依赖 + doc-lens-dsh 薄适配器）。其余：配置单源+zod schema 启动校验、加 `openapi-schema` 提取器（SSOT 上移机器契约）、stage gate 强制化、测试补齐。
**反转条件（改选重写 B）**：重建后 evoucher 抛弃 dsh/cordis 宿主 / 宿主 RC 动荡不可 vendor / 要求 doc-lens 升格系统级完整性层（契约+代码+运行时）。
成本：A=16-21 人日，B=40-60 人日。doc-lens 对 evoucher 生产**零运行时依赖 → 重构零爆炸半径**。

## ⚠️ 命名澄清（修正）：doc-len = doc-lens

用户用 "doc-len" 作为 `/Users/mac/project/dsh-app/dsh-plugin-doc-lens` 的简称。
此前误判为"协议长度字段"（data offset / 报文边界 / 异常检测），全仓搜 `doc-len|docLen|doc_len|DOCLEN`
零命中，唯一匹配是 doc-lens 带 s —— 当时据此下结论"两者无关"，是错的。

用户原问题的真实语义：把 doc-lens 的能力映射到协议/序列化词汇来问 ——
- "数据偏移量校验" = 漂移(drift)核对
- "报文边界划分" = stage 边界（pipeline 阶段分界）
- "数据完整性验证" = 文档一致度(agreement)
- "异常数据检测" = 漂移/异常检测

**关键修正**：doc-lens 内核(model.ts:4-13)第一公民是"事实点(Fact)"而非"文档"，
比对的是**语义事实值**(api-paths/identifiers/regex 从 markdown 提取)，**不是字节偏移**。
所以"仅作数据偏移量校验、作用有限"这个前提不成立 —— 它已是事实级一致性审计器。

### doc-lens 内核实测结论（回答"能否承担更关键职责"）
- 已有：fact-divergence(缺失/自创)、stale-downstream(上游比下游新)、orphan-doc、duplicate-name、config-warning
- 已有 stage 边界概念(StageSpec.order) —— 但**声明式**(config 里写目录)，**非强制式**(不在阶段切换时拦截)
- 已有 adjudication 指纹机制(防闸门自己失效) + `--strict` 门禁(阻断未裁决)
- **没有**：运行时/代码/协议解析能力(ExtractorKind 仅 api-paths|identifiers|regex)；无结构化契约(OpenAPI/Proto)解析；
  无字节级/报文级 framing；"完整性"仅是一致度比值，非哈希/签名级
- 定位结论：doc-lens = **文档/spec 一致性治理层**，不是系统级完整性层。
  重建 evoucher 时 SSOT 应移到机器可读契约(OpenAPI/Proto)，doc-lens 退为"markdown 文档 vs 契约"的桥接校验。

### evoucher 真实协议栈（独立议题，非 doc-lens 职责）
- **外部 EVES**：XML/CFX 报文，交易码 T1001/T1002/T1003/T2001~T2004/T3001/S1001/S1002
- **内部 ngdb**：三段式 JSON over SOFARPC(Bolt)
- **FUNC-42**：XML↔三段式JSON 转换；RULE-080 字段100%覆盖、RULE-083 Base64 OFD 原样透传
- 链路（REQUIREMENTS:626）：验签→核心会计查询+OFD生成→文件签名→CFCA盖章→OSS→报文签名→Base64→返回

### 尺寸约束才是"长度"的真实战场（且已有矛盾）
| 规则 | 内容 | 出处 |
|---|---|---|
| BD-01 | OFD ≤ 4MB | REQUIREMENTS:865 |
| RULE-007 | OFD>4MB 拒绝生成 | REQUIREMENTS:655 |
| **RULE-017** | OFD>4MB → **拒绝** | REQUIREMENTS:736 |

### 更严重的前置风险
**Q-001：EVES 的 CFX 报文详细字段定义从未拿到**（"待EVES运营方提供""无文档阻塞接口开发"）。
这比长度字段高一个量级 —— 契约缺失时，任何分帧/完整性设计都是空中楼阁。

### 结论
- 长度字段 = **分帧原语 + 廉价健全性检查**，不是完整性机制，更不是安全控制
  （位翻转/字段篡改/编码错误都不改变长度；攻击者控内容即控长度）
- 三段式 JSON 与 CFX/XML 均**自定界**，Bolt 自带帧长 → 应用级长度字段**冗余**
- 建议：不做分帧长度字段；尺寸校验下沉业务层（`ofdSize` 之类语义名，校验**解码后**大小）

### 双层治理架构图（已用 Visualizer 渲染，2026-08-30）
SSOT(OpenAPI/Proto) 在顶 → 左 doc-lens 管文档层(stage gate 卡 04→05) / 右 contract tests 管代码+运行时(CI gate 卡 05/运行时) → 底部 Pipeline Gate 两层任一阻断即停。
结论落点：doc-lens 在重建后定位为"markdown 文档 vs 契约"桥接校验器，不当系统级完整性层。
