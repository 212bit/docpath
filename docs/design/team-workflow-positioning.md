# DocPath 多人团队定位与协作路线图

> Status: Accepted direction
> Date: 2026-06-13
> Scope: 产品定位与路线图边界；本文不定义立即实现契约。

## 1. 定位结论

DocPath 当前阶段不应定位为个人轻量工具，也不应过早定位为企业合规平台。

当前定位：

> DocPath 是面向多人 / 多 Agent 开发团队的 AI 工作流状态层。

更直接的产品表达：

> DocPath 让 AI 开发团队知道任务现在在哪里、谁该接手、能不能继续、出了问题怎么恢复。

DocPath 的核心价值不是替 AI 做决定，而是把 AI 开发过程中的任务状态、交接、门禁、决策和恢复路径变成团队共享的、可校验的工作轨道。

一句话原则：

> AI 负责推理和执行；DocPath 负责共享状态、流程门禁和恢复证据。

## 2. 目标用户

### 2.1 主要用户

- 2-10 人开发团队：多人共同使用 AI coding agent 推进同一个代码库。
- 多 Agent 协作团队：同一项目中可能由 Codex、Claude、OpenCode 或不同 Agent 会话接力。
- 开源维护团队：需要让后来者快速理解任务状态、决策背景和验证结果。
- 长任务执行者：经常遇到上下文中断、Agent 断线、任务恢复和重复判断问题。

### 2.2 不优先服务的用户

- 纯个人一次性脚本用户：这类用户更在意速度和低仪式感，DocPath 可以兼容，但不是路线图主轴。
- 大企业合规采购方：这类用户会要求 RBAC、SSO、审计报表、留存策略和权限矩阵，当前阶段不进入。
- 通用 prompt 工具用户：DocPath 不把自己做成 prompt 管理器或 Agent 编排器。

## 3. 要解决的问题

多人 / 多 Agent 团队的痛点不是“缺少更多 AI 自由度”，而是共享事实不稳定：

| 协作问题 | 没有 DocPath 时的表现 | DocPath 应提供的能力 |
|---|---|---|
| 当前状态不清 | 新成员要读聊天、git log 和散落文档重新判断 | `status` / `next` 给出当前阶段、下一步和阻塞点 |
| 交接断裂 | 上一个 Agent 的上下文丢失，后来者重新探索 | `breadcrumb` / `handoff` 提供恢复路径和责任转移记录 |
| 门禁失效 | AI 在聊天里声称完成，但没有验证证据 | `check` / `review` 把完成声明变成可验证门禁 |
| 决策漂移 | 同一定位、架构或流程问题反复讨论 | `decisions` / `journal` 沉淀可复用结论 |
| 多 Agent 冲突 | 不同会话重复推进、覆盖状态或抢任务 | CLI 状态机、锁和任务归属提供一致性边界 |

## 4. CLI 为什么仍然必要

在个人工具里，AI 直接写 markdown 状态文件有时足够；在多人团队里，状态文件必须成为共享事实源，不能完全依赖自由文本。

DocPath CLI 的价值应从“企业审计控制”改写为“团队共享事实源”：

| 能力 | 不再主打的企业说法 | 多人团队说法 |
|---|---|---|
| CLI 写状态 | 合规审计入口 | 团队共享事实源 |
| FSM | 企业级流程控制 | 团队不会迷路的任务轨道 |
| `next --agent` | 自动化管控 | 新成员 / 新 Agent 的恢复入口 |
| `check` / `review` | 审批门禁 | 团队质量卡点和完成证据 |
| `breadcrumb` | 审计痕迹 | 断点恢复和接力记录 |
| `handoff` | 上下文归档 | 责任转移和剩余风险说明 |
| `decisions` / `journal` | 留存策略 | 防止重复争论和定位漂移 |
| 文件锁 | 企业并发一致性 | 多 Agent 不互相覆盖 |

边界原则：

- 自然语言可以降低调用摩擦，但不能绕过 CLI 写运行态。
- AI 可以建议下一步，但状态落账必须通过 DocPath 生命周期命令。
- 角色、prompt、payload 和 deliverables 都是上下文与证据增强，不替代 `.docpath/workspace/state.json`、task、backlog 和 breadcrumb。

## 5. 非目标

当前阶段明确不做以下能力：

- 完整 RBAC。
- SSO。
- 法务 / 合规审计报表。
- 不可篡改账本。
- 多租户企业控制台。
- SOC2 / ISO 采购叙事。
- 自动多 Agent 编排器。
- 默认 worktree 并行执行。
- 通过标签、watch 或自由文本输出直接驱动状态转移。

这些能力不是永久拒绝，但不应进入当前产品主叙事。只有当多人团队协作闭环已经稳定，并且真实用户明确需要企业采购能力时，才应重新评估。

## 6. 路线图重排

### P0: 团队协作最小闭环

目标：让团队成员或新 Agent 能可靠接手任务。

- 交接质量：`handoff` 应明确下一步、剩余风险、修改范围、验证状态和责任转移。
- 恢复入口：`current` + `breadcrumb` + `next --agent` 应让接手者快速判断当前状态。
- 任务归属：引入轻量 owner / assignee / agent-session 元数据，先解决责任不清，不做复杂权限。
- 门禁可见：`check` / `review` 需要清楚说明阻塞原因、通过证据和下一步动作。
- 决策防漂移：定位、架构、流程级结论应进入决策文档或任务证据，避免在聊天中反复重置。

### P1: 多 Agent / 多人并发

目标：让多个会话或多个工具在同一项目中有可控协作边界。

第一步实现边界见 `docs/design/session-isolation-mvp.md`：先保持单 active task，
通过 session identity、task/step lease、breadcrumb attribution 和关键写入锁来
解决多会话覆盖与归属问题；`status --team` 与真正 multi-active task runtime
放到后续阶段。

- Agent/session 标识：记录当前执行者和会话来源，支撑交接与冲突判断。
- 冲突检测：发现多个执行者同时推进同一任务或修改同一状态路径时 fail-loud。
- 团队状态视图：提供 `status --team` 或等价视图，展示可接手、阻塞、执行中和待验证任务。
- 子任务证据：允许 role/payload/deliverables 作为证据挂到任务，但主 FSM 仍保持单一状态真源。
- backlog grooming：按多人团队定位重新筛选 backlog，降低企业合规项优先级。

### P2: 体验与调用摩擦

目标：降低 Agent 和团队成员正确使用 DocPath 的成本。

- Prompt 标准化：提供更稳定的 Agent 操作模板，减少漏跑 `next/check/review`。
- 自然语言入口：把“继续上个任务”“交接给下个 Agent”等请求翻译成 CLI 路由，而不是绕过 CLI。
- 错误解释：当状态机拒绝转移时，用团队协作语言解释原因和恢复路径。
- 角色上下文：继续强化 product/design/software/qa role context，但角色输出必须落盘到任务证据。

## 7. 后续任务拆分建议

建议从以下 backlog 切片继续推进：

1. 强化 `handoff` 交接包：要求包含下一步、风险、修改文件、验证状态和责任转移摘要。
2. 引入轻量任务归属元数据：支持 owner / assignee / agent-session，不实现权限控制。
3. 增强 `next --agent` 恢复说明：让新 Agent 能看到为什么推荐该命令，以及阻塞条件是什么。
4. 增强门禁可见性：让 `check` / `review` 输出更明确地区分失败原因、修复建议和可继续条件。
5. 设计 `status --team`：先输出只读团队视图，不做 Web 控制台或企业管理台。
6. 设计多 Agent 冲突检测：基于当前任务、pending-done 哨兵、文件锁和 session 标识做最小实现。
7. 重排 backlog：把企业合规项降级，把团队交接、恢复和门禁可见提升为近期主线。

## 8. 成功信号

短期成功信号：

- 新 Agent 接手当前任务时，不需要重新阅读大量聊天记录就能判断下一步。
- 每次 handoff 都能说明谁接手、剩余风险和验证状态。
- 任务完成声明能回溯到 check/review 证据。
- 定位、路线图和非目标不再反复在个人工具与企业合规平台之间摇摆。

失败信号：

- 继续增加命令，但接手者仍然不知道下一步。
- 产品叙事滑向企业合规，导致近期任务开始围绕 RBAC、SSO、审计报表展开。
- Prompt、角色或自然语言入口绕过 CLI 状态机，导致 `.docpath/` 失去共享事实源地位。

## 9. 与既有设计文档的关系

本文收敛 `docs/design/agent-integration.md` 中的 agent-native workflow substrate 方向，把它产品化为“多人 / 多 Agent 团队的 AI 工作流状态层”。

本文也重排 `docs/design/next-phase-tasks.md` 的后续优先级：状态与门禁稳定化仍然重要，但产品解释应从“Agent 工作流内核”进一步收敛为“团队协作闭环”。多 Agent 适配不再只是安装协议生成，而应服务交接、恢复、冲突检测和团队状态视图。
