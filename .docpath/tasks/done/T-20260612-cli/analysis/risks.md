## 1. 产品风险

- 交互式问题过多会让 init 变慢，反而降低首次体验。
- 文档示例如果覆盖太多工作流细节，会偏离 getting started 的最小路径。
- 错误提示若只改 init，用户可能期待所有命令都有同等体验。

## 2. 设计风险

- TTY prompt 对 Agent 和 CI 不友好，必须只在显式 `--interactive` 下触发。
- 默认选项选择不当可能导致用户误覆盖 `.docpath`。
- 中文文案过长会让终端输出不易扫描。

## 3. 技术风险

- `@clack/prompts` 在非 TTY 下可能返回 cancel 或挂起，需要明确 guard。
- 测试 TTY 交互可能不稳定，优先把交互决策函数拆小，或用可控 stdin/PTY 测试最小路径。
- init 涉及写多文件，任何新增 prompt 都不能破坏现有初始化原子性假设。

## 4. 交付风险

- 同时做 interactive、错误提示、文档可能范围膨胀。MVP 应聚焦 init 相关体验，不扩展到所有 CLI 命令。
- 若全量测试耗时过长，可先跑聚焦测试和 typecheck，再在收口运行全量测试。

## 5. 缓解措施与触发条件

- 交互问题不超过 2-3 个，默认使用自动检测值。
- 已存在 `.docpath` 默认只注册，不覆盖。
- 非 TTY 立即失败并打印替代命令。
- Getting started 只覆盖最小闭环，深入内容留给后续文档。
