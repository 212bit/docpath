> backlog_id: R-160

## 1. 背景与动机

DocPath 的产品叙事需要从“企业级审计合规层”收敛为“多人 / 多 Agent 团队的 AI 工作流状态层”。企业合规叙事虽然能解释 CLI、FSM、check/review、breadcrumb、handoff 的强约束价值，但会把路线图过早拖向 RBAC、SSO、审计报表、不可篡改账本和多租户控制台。

更准确的当前阶段定位是：DocPath 服务 2-10 人开发团队、开源维护团队、以及多人 / 多 Agent 协作团队。它解决的核心问题不是法务审计，而是团队在 AI 开发过程中的共享状态、交接、门禁、恢复和决策不漂移。

## 1.1 产品定位

> DocPath 是面向多人 / 多 Agent 开发团队的 AI 工作流状态层。AI 负责推理和执行，DocPath 负责把任务状态、交接、门禁、决策和恢复路径沉淀成团队共享的、可校验的工作轨道。

更短的产品表达：

> DocPath 让 AI 开发团队知道任务现在在哪里、谁该接手、能不能继续、出了问题怎么恢复。

## 1.2 目标用户

- 多人开发团队：需要在成员之间交接 AI 辅助开发任务。
- 多 Agent 协作团队：同一项目中可能由 Codex、Claude、OpenCode 或不同会话接力。
- 开源维护者和小型产品团队：需要保留任务状态、决策背景和验证证据，但不需要企业合规平台。
- 长任务执行者：经常遇到上下文中断、Agent 断线、任务恢复和重复判断问题。

## 1.3 核心用户任务

- 新成员或新 Agent 能在短时间内知道当前任务阶段、下一步和阻塞点。
- 团队能判断任务是否通过 check/review 门禁，而不是依赖聊天中的口头完成声明。
- 交接时能看到责任、剩余风险、修改范围和恢复路径。
- 决策能沉淀到合适位置，避免同一定位问题反复摇摆。

- 目标: 明确 DocPath 当前阶段面向多人 / 多 Agent 团队，核心价值是共享状态、交接、门禁、恢复和决策不漂移。

- 可选方案:
  - 个人工具定位: 更轻、更易传播，但难以解释 24 状态 FSM、门禁、锁和 handoff 的必要性。
  - 企业合规定位: 能解释强约束，但会迫使产品过早进入 RBAC、SSO、审计报表和合规采购场景。
  - 多人团队定位: 保留 DocPath 的状态机和 CLI 价值，同时把近期路线图控制在小团队协作问题上。
- 推荐方案: 采用多人 / 多 Agent 团队定位，把 CLI 表达为团队共享事实源，把 FSM 和门禁表达为协作轨道，而不是企业合规控制面。
- 不做什么: 本任务不实现企业权限、不可篡改审计、合规报表、多租户控制台、自动多 Agent 编排或状态 watch 机制。
