## 背景

依据 `.docpath/workspace/trace.jsonl` 实测：最近 200 条调用记录的 `session` 键**全部为 `session-default`**，说明"按终端/任务键区分会话"的隔离机制在当前环境**实际未生效**（P0-B 会话键控曾名义合并，但本工作区数据证明未落地）。

后果（token 层面的连锁）：会话无法区分 → 多任务并行或快速切换时，`next`/`status` 解析出的 current task 可能属于另一条会话 → 返回的 `next_action`/`recommended_command` 与 Agent 正在做的任务不符 → Agent 不信任任何单次确认，被迫反复 `next` 校验。实测 **`next`+`status` 合计 215 次，占全部调用 14.3%**，其中相当一部分是"因为不信上次结果而重复确认"。

这些确认 turn 的代价不在输出长度（`next --agent` 仅 ~1800 字符），而在于**每次确认都强制平台把整段对话历史重新过一遍**——见成本模型 \(C(N)=N\cdot B+\delta\cdot N^2/2\)。会话隔离失效直接把"确认类 turn"的数量抬高。

根因待诊断（执行时先定位再修，勿盲改）：可能是
1. 运行环境未提供稳定的终端/会话标识（TTY id、终端环境变量缺失）；
2. key 生成逻辑在缺标识时回落到 `session-default` 而非派生唯一键；
3. hook 未把会话标识透传给 CLI。

## 验收

- [ ] 先产出可复现诊断：在同一 docpath 项目并发开两个会话（两个终端/两个任务）时，打印两条会话各自的 session 键，确认当前恒为 `session-default` 的具体环节。
- [ ] 修复后，并发两会话在 `trace.jsonl` 中的 `session` 键必须**不同且各自稳定**（同会话内多命令保持同键）。
- [ ] `next`/`status` 的 context 解析按 session 键隔离，跨任务不再返回错误的 current task 与 next_action。
- [ ] 明确回落策略：当确实拿不到终端标识时，应基于 cwd + 活动 taskId 派生可区分键，而不是全部塌缩到 `session-default`。
- [ ] 补/更新会话隔离测试覆盖"双会话不串味"；全量测试与 typecheck 通过，零回归。
