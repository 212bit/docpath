## 处置结论（2026-09-07）

**关闭：前提证伪，非缺陷。** 完整取证见 `backlog/analysis/R-320-analysis.md`（证据引用已挂 analysis）。

要点：

1. **成本模型记错账**：\(B\)≈15–25k 是 agent 每个普通 turn 都要付的上下文成本，去重救不了；一个冗余 `next` 独有的可省开销只有 tool result 本身——实测全量快照 2583 字节（主仓）/ 1698 字节（e2e fixture），≈0.7–1k token。
2. **实际冗余小**：trace 全史 217 次 next+status 中，中间无状态变更命令的连续对仅 39 个，且含会话启动/恢复等 AGENTS.md 要求的合法确认。全史可省上限 ≈ 40k token。
3. **prompt caching 中和二次项**：历史前缀按缓存读计价，\(\delta N^2/2\) 基本被平台消化。
4. **技术可行但代价不成比例**：哈希持久化使只读的 `next` 变写命令；workspace 级哈希在多会话下会让从未见过全量快照的 agent 收到 `status_unchanged`，破坏恢复安全；防御性 agent 会恒带 `--refresh` 使节省归零。

三条 P0（R-318/R-319/R-320）的共同根因：把平台已消化、或任何 turn 都要付的成本记到了 DocPath 头上。本条不再立项；若未来引入多会话并发观测或宿主无 prompt caching，可按 P3 重新评估。

## 原背景（保留供溯源）

R-317/S2 已把 `next --agent` 静态字段瘦身（单次输出 ~1800 字符），但未压"确认次数"。方案原设想：计算覆盖路由字段的快照哈希持久化到 workspace，无变化返回单行 `status_unchanged`，`--refresh` 强制全量。
