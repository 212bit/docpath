## 背景

[来源: 2026-07-13 R-266 收尾复盘] 一个工作树混了三类未提交/已 commit 产物
（R-266 已 commit 主体 cb809b1 / R-250 漂泊实现 / R-260 落库产物），
`changes --agent` 把三类全归当前 task（R-266）标题，靠**人工三段分离 commit**
方解开。`changes --agent` 的 `suggested_commit_message` 永远是当前 task 标题，
缺乏跨 task 归组能力。

### 与 R-260 的切分关系（关键）
本条的 FR-5/FR-6 原属 R-260（《done 阶段业务代码未 commit 软提醒门控》），
2026-07-14 promote R-260 为 task `T-20260714-done-commit` 时，这两条 FR
随 R-260 spec 一起进 active task 的 spec.md。复盘判定：
`changes --agent` 的归组能力改 changes 命令行为，与 done 软提醒改 done 命令行为
**属两个不同命令的行为改动、scope 不同**，混在 R-260 task 里会让 plan/review 都
难做（scope mismatch 正是 R-255 family 的痛点）。

故采 **β-3 改动顺序**：R-260 task 继续 FR-1~4（done 软提醒，level 1 路径独立推进），
本条 R-262 立为独立 backlog level 2 入口，承载 changes 归组能力。**active task
spec 切分不在 R-260 drafting 阶段做**（避免 [[docpath-write-spec-taskid-rebind]]
的 task identity drift），而是等 R-260 task done、active slot 空时，R-262 正式
promote 为自己的 task，再在 R-262 的 write-spec sink 流程里 clean-fill FR-5/FR-6
（此时 R-260 已 done，R-260 的 spec 不再变化，无 drift 风险）。

期间 R-260 的 spec.md（T-20260714-done-commit）**暂时仍含 FR-5/FR-6 占位**，
是已知分叉源，本条目的存在即为收口这个分叉源。

## 核实事实（2026-07-13 现场）
- `src/commands/changes.ts` 输出 `recommended_stage_command: null`（无 staged 时不给命令）
  + `suggested_commit_message` 永远取 current task 标题。
- `src/utils/changes-report.ts` 的 `blockingReasons` 仅按 worktree_isolation 分组，
  不按 canonical task evidence 路径（`.docpath/tasks/<task_id>/*`）匹配归当前 task。
- `changes --agent` 不支持 `--task <id>`/`--scope <file-list>` 显式归组。

## 需求（从 R-260 切分而来）
- **FR-5**：`changes --agent` 在多需求混合工作树时给出 task-aware 文件分组提示：
  按 canonical task evidence 路径（`.docpath/tasks/<task_id>/*`）匹配归当前 task；
  其余（如别 task 的漂泊实现、backlog 落库、跨需求共享文件）单独列出并标注
  "可能不属于当前 task"，而非全归 current task 标题。
- **FR-6**：`changes --agent` 支持 `--task <id>` 或 `--scope <file-list>` 显式归组，
  让 agent 能为非当前 task 的改动单独生成 commit 建议（如漂泊实现需以其真实
  需求名义提交，而非当前 task 标题）。

## 关联 backlog（关联而非依赖）
- **R-249**：dirty worktree 分流（`isDocPathManagedPath`/`nonDocPathFiles`）已可用，
  本条 FR-5 复用同一现成分流做文件分组匹配，不阻塞。
- **R-254 / R-255**：review scope 推导 family。本条不直接消费 review scope，
  但 changes 文件集影响 review 的 changedFiles 推导 —— R-254 的 last_commit
  fatal 修好后，changes 显式 --scope 可作为 review scope 的上游稳定输入。
- **R-260**：source backlog；R-262 由 R-260 切分而来，R-260 完成 FR-1~4 后
  active slot 释放，R-262 再 promote。

## 约束
- changes --agent 仍是 read-only 报告（CLAUDE.md），不抢 commit 执行权，
  只给归组提示与建议命令。
- 不破坏现有 `ready_to_commit`/`blocking_reasons` 语义，仅扩展归组维度。
- level 2 任务：promote 前需 `readiness: analyzed` + `evidence.analysis`
  （按 missingReadinessEvidence 对 level≥2 的要求），**含考虑 changes 命令
  跨 agent/worktree 使用时的归组边界 + R-249 分流复用 + 与 review scope 上游
  关系**的 analysis。

## 验收
- 多需求混合工作树时，changes --agent 输出把当前 task canonical 路径文件与
  非 canonical 文件分开列，并标注"可能不属于当前 task"。
- `changes --agent --task <id>` 给出该 task 的 commit 建议（即使它非 active）。
- `changes --agent --scope <file-list>` 给出指定文件集的归组 + commit 建议。
- 回归：单 task 干净工作树时，输出与现状（按 worktree_isolation）一致，无回归。
- (与 R-260 解耦的判定)R-262 不依赖 R-260 done —— 但 promote R-262 时
  R-260 应已 done，使 active slot 空且 spec 切分无 drift。
