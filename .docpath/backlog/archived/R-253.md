## 背景
[来源: codex session 挖掘 @ evoucher 2026-07] 多次出现 agent 手动修正: "DocPath 把 S1 主条目标成完成，但底部 checklist 没同步勾选"、"DocPath 已把 S4 小节标成完成，但底部 Checklist 还没"。`docpath agent step --status done` 更新主步骤状态时未同步 plan.md 底部 checklist 对应项。

## 代码核实 (2026-07-06，docpath 项目现场复现)
- `src/commands/agent.ts:183` 已调用 `markPlanStep` 同步 checklist，失败有 warning。代码层已有同步逻辑，R-253 不是"没同步"而是"只同步了一处"。
- 现场复现（R-248 任务 plan.md）: plan.md 有**两份** checklist：
  1. 每个 `### S3:` section 内的 `- [x] S3: 验证验收标准`（section 内 checklist）
  2. `## Checklist` 下的 `- [ ] S3`（底部汇总 checklist）
- `docpath agent step --status done` 后，section 内的更新成 `[x]`，但底部 `## Checklist` 的同 id 行**仍是 `[ ]`**。
- 根因 `src/utils/plan-sync.ts:110-118` `markPlanStep`: 只用 `target.lineText`（第一个匹配）+ `target.checklistIndex` 替换**一处**，不更新同 id 的其他 checklist 行。
- `src/utils/doc-parser.ts:108-121` `parsePlanSteps` 的 `checklistById` 用 `continue` 跳过重复 id，只保留第一个匹配（section 内优先），底部的被忽略。
- 与 R-251 同链条: agent 因 checklist 不同步，转而 apply_patch 手编 plan.md，触发 sha256/current-canonical 漂移。R-251 修了阶段回退（agent 敢用 write-plan 了），R-253 修了 checklist 同步，整条链路才彻底闭合。

## 验收
- `markPlanStep` 更新 plan.md 时，同步更新**所有**匹配该 step id 的 checklist 行（section 内 + 底部 `## Checklist`），而非只第一处。
- 回归: agent step --status done 后，plan.md 的 section 内 checklist 与底部 Checklist 同 id 行均变为 [x]。
- 回归: parsePlanSteps 对同 id 多 checklist 行不丢失（用于 drift 检测）。
