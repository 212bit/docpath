## 背景
[来源: docpath 项目现场，R-251 修复过程中复现] `docpath review` 在代码本身 0 错误 0 警告（current_diff 与 baseline 均干净）时，仍因 Review Skill Gate 报 `invalid_evidence: file set mismatch` 阻塞，必须用 `--skip-skill-review <skill> --reason <reason>` 手动豁免才能通过。friction: 正常代码被 skill 证据元数据问题卡住。

## 代码核实 (2026-07-06)
- `src/utils/review-skill-router.ts:187` `validateEvidenceForRequirement`:
  `if (!sameFileSet(evidence.files, requirement.files)) return 'file set mismatch';`
- `sameFileSet` (line 171-175) 用**严格全等**比对：长度+排序后逐项 ===。
- requirement.files 由 review skill 按 diff 推导期望审查的文件集；evidence.files 是 Claude 用 `docpath write-review-skill` 生成证据时记录的文件集。两者任意一项不一致（顺序、范围、路径形式）即 mismatch。
- mismatch 后 `commands/review.ts:345` 把 invalid_evidence 当阻塞项，`failed = missingEvidence.length > 0 || invalidEvidence.length > 0`（router.ts:241），与"代码有缺陷"同等阻塞，即使 current_diff 0 错误。

## 根因
file set mismatch 的语义本应是"evidence 过期/不匹配，请重生成或确认范围"，是**证据元数据问题**，不应等同于"代码缺陷阻塞"。当前设计把两者混为一谈，导致：
- 代码干净但仍被阻塞，需手动 skip-skill-review（R-254 又暴露 skip 流程本身易 crash）。
- agent 不清楚该重生成 evidence（跑 write-review-skill）还是修代码。

## 验收
- review 检测到 file set mismatch 时，给出明确指引：要么提示"重生成 evidence: docpath write-review-skill --skill <skill> ... --stdin"，要么提供 `--fix-skill-evidence` 就地重建。
- 或：区分"证据元数据问题"与"代码缺陷"——前者降级为告警+修复提示，不阻塞 review；只有 current_diff/baseline 的真实 finding 才阻塞。
- 回归: 代码 0 错误时，file set mismatch 不再强制阻塞 review（给出修复提示即可）。
