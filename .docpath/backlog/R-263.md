## 背景

[来源: 2026-07-14 R-260 立项实操] promote R-260 成 task
`T-20260714-done-commit` 时发现两条结构化任务真源同步的工具行为
**未在 CLI 层显式告知 agent**,易让 agent 误以为 spec 已结构化进
真源,实际 spec.json 仍是笼统单条 FR-1,直到走 `write-spec --stdin`
才同步。

### 核实事实（2026-07-14 现场实测）

**Claim A —— promote 生成的 spec.md 里 FR checklist 仅 1 条笼统 FR-1**
- `src/commands/backlog.ts:468-530` `renderPromotedSpec`:
  line 525 生成 `### 功能需求` 段时只塞
  `- [ ] FR-1: ${item.title}`(把 backlog **标题**作整条需求塞进单条 FR)。
- brainstorm 在 backlog body 里用 yaml 代码块写的 `FR-1~4` 真实条目,
  经 `parseBacklogBody` 进 `backgroundSection`(背景段)原样塞,**不会被
  parseSpecMarkdownDocument 的 `parseChecklistItems(md, 'FR')` 收集**
  (后者只扫 `- [ ] FR-N:` checklist 行,不扫 yaml 代码块)。
- 结果:promote 落盘的 spec.json 真源 `functional_requirements` 只有 1 条
  `FR-1: <笼统标题>`,brainstorm 的真实 FR-1~4 不进真源。
- 实证:R-260 promote 后 spec.json 仅 `FR-1: done 阶段业务代码未 commit
  软提醒门控`(一行笼统);走 `write-spec --stdin` 重写成 checklist 形式
  (`- [ ] FR-1: detection ...` 等 4 条)后,spec.json 才真实含 FR-1~4。

**Claim B —— `write-spec --stdin` 才同步 spec.json 真源**
- `src/commands/write-spec.ts:116` `writeActiveTaskFile(docpathDir,
  taskId, 'spec.md', specContent)` → `src/utils/task-files.ts:49-54`
  对 `isStructuredTaskMarkdownFile('spec.md')` 触发 `writeStructuredTaskJson`,
  → `src/utils/structured-docs.ts:679` `parseStructuredDocument(spec.md)`
  → `parseSpecMarkdownDocument` 把 markdown 解析成结构化 doc → 写 spec.json。
- 即:**手改 spec.md(手 Edit)不更新 spec.json 真源**;只有走
  `write-spec --stdin`/`--content` 才触发 spec.md→spec.json 解析同步。
- spec.json 是 `structured-docs.ts` 自注释的"truth source"(`Read JSON
  (always, it's the truth source)`,line 680),spec.md 是渲染/可读 view。
- 实证:R-260 demote 时必须 `write-spec --stdin`,若手改 spec.md 改 major
  gate 开关,spec.json `major_change_gate.required` 不会变(真源分叉)。

### 影响
- agent promote 后若直接 `docpath plan`,plan emitter 拿到 spec.json 真源里
  只有笼统 FR-1,plan 拆出的子任务无方向(plan 难基于真实 FR-1~4 拆 S1~S5)。
- agent 手改 spec.md 改 spec 但不跑 write-spec → spec.json 真源与 spec.md
  长期分叉,后续 `check`/`drift` 可能触发 [[docpath-write-spec-taskid-rebind]]
  同款真源不一致告警,但根因不同(本条是工具行为未前置告知)。
- 跨 agent 一致性差:Claude Code agent 知道走 write-spec、Codex agent 可能
  手 Edit spec.md → 两个 agent 对同一 task 的真源认知不一致。

## 需求

- **FR-1（promote 侧）**:`renderPromotedSpec` 若 backlog body 含 checklist
  形式(或可解析)的 FR 条目,直接用作 spec.md 的 `### 功能需求` checklist
  (而非把 title 作单条 FR-1);无 checklist 形式 body 时,回退当前行为
  (单条 FR-1 = title)。可借助新增 `parseBacklogChecklist(body, 'FR')` 解析。
- **FR-2（CLI 提示侧）**:`docpath promote` 输出与 `docpath next --agent`
  hints 显式标注:"spec.json 真源已生成,如需细化 FR/AC 请用
  `docpath write-spec --stdin`(手改 spec.md 不更新真源)"。
- **FR-3（防误改侧,可选）**:`write-spec` 之外任何对 spec.md 的直接 Edit,
  在 `docpath check` 或 doctor 里给出真源分叉告警(spec.md 与 spec.json 的
  content_sha256 不一致时提示)。

## 验收
- backlog body 含 `- [ ] FR-N: ...` checklist 形式时,promote 生成的 spec.json
  真源 `functional_requirements` 含全部 FR,而非单条笼统 FR-1 = title。
- `docpath promote` 输出含一行"真源同步提示"指向 write-spec。
- 文档侧:DocPath 使用文档补一节"spec 真源同步语义:write-spec 才同步 spec.json,
  手改 spec.md 不生效"。
- 防回归:R-260/R-262 立项场景重新跑一遍,FR 真源完整进 spec.json。

## 范围
### 包含
- `renderPromotedSpec` checklist 拆分(FR-1)
- CLI 提示前置化(FR-2)
- 可选真源分叉告警(FR-3,P3)

### 不包含
- 改变 spec.json 作为真源的地位(机器真源保持)
- changes --agent 归组(R-262 范畴)
- journal dry-run 预览(R-261 范畴)
