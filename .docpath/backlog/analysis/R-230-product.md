# DocPath UI Design - Product Analysis

## 1. 用户价值与成功指标

### 用户价值
- **效率提升**：通过可视化仪表盘，2 秒内定位需要人工介入的阻塞点，而非逐个项目运行 `docpath status`
- **认知负荷降低**：状态机流转图可视化，新手更容易理解 DocPath 的 Phase/Gate 模型
- **错误预防**：Attention Queue 主动提示，避免遗漏失败的门禁检查

### 成功指标
- **主观指标**
  - 用户调研：90% 认为 Dashboard 比纯 CLI 更直观
  - 美观度评分：从 6/10 提升到 8/10（设计前后对比）
- **客观指标**
  - Dashboard 打开频率：每日活跃会话 > 50%
  - 平均停留时间：3-5 分钟（快速巡检）
  - 错误恢复时间：从发现问题到定位根因 < 30 秒

## 2. 核心用户旅程

### Journey 1: 早晨工作流健康检查（5 分钟）
1. 打开浏览器访问 `http://localhost:5178`
2. 扫描 "All Projects" 视图，Attention Queue 显示 2 个失败项
3. 点击第一个失败项目，跳转到单项目视图
4. 查看 Gates 页面，发现 Review 门禁有 3 个 error
5. 点击错误详情，复制命令到终端修复
6. 点击 Refresh，确认问题已解决

### Journey 2: 并发开发状态监控（持续）
1. 在 Worktrees 页面，看到 3 个活跃工作树
2. 识别出一个 session lease 已过期 2 小时
3. 点击 "Release Lease" 按钮，确认释放
4. 切换到对应项目的 Workboard，恢复任务执行

### Journey 3: 需求优先级排序（10 分钟）
1. 进入 Backlog 页面，看到 15 个 raw requirements
2. 按优先级筛选：P0 有 3 个，P1 有 7 个
3. 点击某个 R-230，展开详情查看 evidence 和 context
4. 决定提升为任务，复制命令 `docpath backlog promote R-230` 到终端

## 3. 业务规则与运营约束

### 数据刷新机制
- 手动刷新：点击 "Refresh" 按钮
- 自动刷新：每 30 秒轮询一次（可配置）
- 实时推送：未来可考虑 WebSocket，但非 MVP

### 权限模型
- Dashboard 是只读视图，执行命令需用户在终端确认
- Modal 中的命令执行通过后端代理，记录日志但不持久化

### 多项目隔离
- 每个项目有独立的 `.docpath/` 状态目录
- Dashboard 通过文件系统读取，不依赖数据库

## 4. 竞品/替代方案与取舍

### 竞品对比
| 工具 | 优势 | 劣势 | DocPath 取舍 |
|------|------|------|--------------|
| Linear | 精美的任务看板、流畅动画 | 重量级、需云端账号 | 借鉴卡片设计，但保持轻量本地化 |
| GitHub Projects | 与 Git 深度集成 | 信息密度过高、配色冷淡 | 学习状态标签设计，但更温暖 |
| Obsidian Canvas | 自由画布、Markdown 原生 | 不适合结构化工作流 | 借鉴温暖配色，但保持列表/表格布局 |

### 设计取舍
- **选择温暖色调** vs 工程工具惯用的蓝/紫：体现品牌差异化，避免 "又一个 dev tool"
- **保持 CLI 优先** vs 全功能 GUI：Dashboard 是观察窗口，不试图替代命令行
- **单体应用** vs 微前端：当前规模不需要复杂架构，保持简单

## 5. 发布策略与灰度/回滚

### 发布计划
- **Phase 1（本次）**：视觉重设计，不改变数据结构和 API
- **Phase 2（未来）**：增强交互（拖拽排序、内联编辑）
- **Phase 3（未来）**：实时协作（WebSocket 推送）

### 灰度策略
- 通过环境变量 `DOCPATH_UI_THEME=warm` 切换新旧主题
- 默认保留旧主题 2 个版本，观察反馈

### 回滚预案
- CSS 独立文件，可快速回退到旧版 styles.css
- 组件改动控制在样式层，不涉及状态逻辑
