# DocPath UI Design - Open Questions

## 1. 必问问题（阻塞 spec）

### Q1.1：是否全面切换到浅色主题，还是保留深色选项？
- **背景**：当前 Dashboard 使用深色 Obsidian 主题，改造后计划使用温暖浅色
- **为何阻塞**：影响设计范围和工作量
- **选项**：
  - A. 仅实现浅色温暖主题，移除深色（简单，但可能流失深色爱好者）
  - B. 同时维护深色和浅色两套主题（工作量翻倍）
  - C. 先实现浅色，保留深色主题切换入口（推荐）
- **推荐**：选项 C，先实现浅色温暖主题，保留 `theme` 切换逻辑，深色主题作为 fallback

### Q1.2：Terracotta 强调色是否需要调整以满足可访问性？
- **背景**：#C4612F 在 #F7F4EF 背景上的对比度约为 4.1:1，略低于 WCAG AA 标准（4.5:1）
- **为何阻塞**：影响设计系统的核心变量
- **选项**：
  - A. 使用 #C4612F，接受对比度风险（更美观，但可能不合规）
  - B. 调整为 #A94E22（深 terracotta），对比度 5.2:1（合规，但略失温暖感）
  - C. 仅在文本使用 #A94E22，装饰元素（边框/背景）使用 #C4612F（混合策略）
- **推荐**：选项 C，关键操作和文本使用深色，装饰元素保留浅色

### Q1.3：是否需要引入照片/插图资源？
- **背景**：design_sense 提到"一个大型 framed 真实照片（Unsplash）"
- **为何阻塞**：影响开发工作量和版权管理
- **选项**：
  - A. 不使用照片，保持纯色背景（MVP，快速交付）
  - B. 在 Hero 区域使用 Unsplash 占位图（需手动选择合适图片）
  - C. 使用抽象 SVG 插图（需设计或购买）
- **推荐**：选项 A（MVP 阶段），留待 Phase 2 优化

## 2. 可延后问题（不阻塞 MVP）

### Q2.1：是否需要动画库（如 Framer Motion）？
- **当前状态**：仅使用 CSS transition 实现简单动画
- **影响**：若需复杂动画（如拖拽排序、页面切换），可能需引入动画库
- **建议**：MVP 阶段使用 CSS transition，Phase 2 再评估

### Q2.2：Dashboard 是否需要实时刷新（WebSocket）？
- **当前状态**：手动刷新或 30 秒轮询
- **影响**：实时性不足，但工作量可控
- **建议**：MVP 阶段保持轮询，Phase 2 考虑 WebSocket

### Q2.3：是否需要设计系统文档（Storybook）？
- **当前状态**：无组件库文档
- **影响**：后续维护成本高，但不阻塞首次交付
- **建议**：Phase 2 建立 Storybook，当前通过代码注释说明组件用法

## 3. 需要用户/业务确认的假设

### 假设 3.1：用户主要在桌面端使用 Dashboard
- **假设内容**：Dashboard 不需要适配移动端（<768px）
- **验证方式**：查看访问日志（若有）或用户调研
- **影响**：若假设错误，需额外适配移动布局

### 假设 3.2：用户习惯使用浅色编辑器
- **假设内容**：大部分开发者的 IDE（VS Code/Cursor）使用浅色主题
- **验证方式**：社区调研或问卷
- **影响**：若大部分用户使用深色 IDE，浅色 Dashboard 可能不协调

### 假设 3.3：用户愿意为美观牺牲少量信息密度
- **假设内容**：温暖设计带来的间距增大不会显著影响效率
- **验证方式**：A/B 测试或用户访谈
- **影响**：若假设错误，需调整行距和字号

## 4. 需要实验验证的问题

### 实验 4.1：Serif 标题在实际场景中的可读性
- **验证方法**：
  1. 在本地环境实现 Fraunces 标题
  2. 邀请 5 名用户阅读 Dashboard 页面
  3. 记录阅读时间和舒适度评分
- **成功标准**：平均舒适度 > 7/10，阅读时间无显著增加

### 实验 4.2：Terracotta 强调色的视觉吸引力
- **验证方法**：
  1. 制作 3 套配色方案：Terracotta / Blue / Purple
  2. 让用户对"温暖感""专业度""辨识度"打分
  3. 选择综合得分最高的方案
- **成功标准**：Terracotta 在"温暖感"和"辨识度"维度得分最高

### 实验 4.3：项目列表的最佳信息密度
- **验证方法**：
  1. 制作 3 种行高方案：紧凑（32px）、适中（40px）、宽松（48px）
  2. 用户测试快速扫描 20 个项目，记录查找时间
  3. 选择查找效率最高的方案
- **成功标准**：适中或宽松方案的查找时间 < 紧凑方案 + 1 秒

## 6. 后续行动建议

### 在 spec 编写前
1. **回答 Q1.1-Q1.3**：明确设计边界和交付范围
2. **对比度验证**：使用 WebAIM 工具验证所有颜色对
3. **制作简易 mockup**：在 Figma 或纸上绘制 Overview 页面布局，获得初步确认

### 在实施过程中
1. **阶段交付**：先完成 Overview 页面，暂停获取反馈，再继续其他页面
2. **持续验证**：每完成一个页面，运行 Lighthouse Accessibility 审计
3. **记录设计决策**：在 `workspace/decisions.md` 中记录重要的 UI 取舍

### 在交付后
1. **收集用户反馈**：通过 GitHub Issue 或社区渠道
2. **监控指标**：Dashboard 使用率、Accessibility 得分、加载时间
3. **规划 Phase 2**：根据反馈决定是否引入插图、动画、实时刷新
