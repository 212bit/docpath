# R-232 分析：修复测试兼容性 - 适配新错误处理系统

## 问题描述

在 T-20260625 (P1 易用性优化) 中引入了新的错误处理系统，导致 3 个 `task-files-drift.test.mjs` 测试失败。

### 失败测试

1. `check reports current/canonical drift with paths and sync fixes it from canonical` (line 218)
2. `check --fix-drift canonical syncs drift before completing checks` (line 259)
3. `check interactively fixes drift from canonical when running in a TTY` (line 274)

所有测试都期望退出码 0，但实际得到退出码 1。

### 根本原因

**旧行为**: `check` 命令检测到漂移时，会报告漂移但仍然返回退出码 0（因为漂移是可修复的，不算失败）

**新行为**: 新的错误处理系统统一使用标准退出码：
- 退出码 1: 用户错误或可恢复错误
- 退出码 2: 系统错误
- 退出码 3: 配置错误

检测到漂移后，新系统通过错误处理路径返回退出码 1。

## 影响范围

- **影响文件**: `tests/task-files-drift.test.mjs`
- **失败测试数**: 3 个
- **其他测试**: 所有其他测试通过（agent、analyze、backlog 等）
- **功能影响**: 无 - 命令行为正确，只是退出码语义变化

## 解决方案

### 方案 A: 修改测试期望（推荐）

**优点**:
- 保持新错误处理系统的一致性
- 退出码 1 更符合"检测到问题"的语义
- 不需要修改源代码

**缺点**:
- 改变了 API 行为（退出码从 0 变为 1）
- 可能影响依赖退出码的脚本

**实施**:
1. 将 3 个测试中的 `assert.equal(result.code, 0)` 改为 `assert.equal(result.code, 1)`
2. 确认输出仍包含预期的消息（漂移报告、修复提示）

### 方案 B: 修改 check 命令保持旧退出码

**优点**:
- 保持向后兼容
- 不需要修改测试

**缺点**:
- 破坏新错误处理系统的一致性
- 需要在 check 命令中特殊处理漂移情况
- "检测到问题但返回 0" 语义不清晰

### 方案 C: 引入新的退出码约定

为可自动修复的问题引入新的退出码（如 4），区分"真正的错误"和"可修复的警告"。

**优点**:
- 更精细的退出码语义
- 脚本可以区分不同类型的问题

**缺点**:
- 增加复杂性
- 需要更新文档和错误处理系统
- 工作量大

## 推荐方案

**方案 A - 修改测试期望**

理由：
1. **语义正确性**: 检测到漂移确实是一个问题状态，返回非零退出码更合理
2. **系统一致性**: 保持新错误处理系统的统一行为
3. **最小改动**: 只需修改测试断言，不涉及源代码
4. **CI/CD 兼容**: 大多数 CI 系统检查退出码非零即失败，这符合预期行为
