## 背景

依据 `.docpath/workspace/trace.jsonl` 全量 1506 条真实调用记录（本工作区实测），`go` 是失败率最高的核心命令之一：

| 指标 | 实测值 |
| :--- | ---: |
| `go` 调用次数 | 147 |
| `go` 失败次数 | 49（**失败率 33%**）|
| 失败中 `gate=none`（步骤顺序不匹配）| **43 / 49（88%）** |

这不是"用户点错"，而是**结构性重试环**：Agent 依据 plan 里列出的步骤顺序发起 `go --step Sx`，但 `go` 对"当前合法可执行步骤"的判定与 plan 列表直觉不一致，于是撞"顺序不匹配"→ 被迫再调 `next`/读 `current.md` 看看到底该走哪步 → 用正确 id 重发。**每个失败制造 2–3 个零信息增量 turn**。

放大机制（为何这是当前最贵的浪费源）：这些重试集中在任务执行中后段，此时对话历史最长。按每任务成本模型

\[ C(N) = N\cdot B + \delta\cdot\frac{N(N+1)}{2} \]

（\(B\)≈每轮固定注入 system+工具schema+AGENTS.md 约 15–25k tokens；\(\delta\)≈每轮历史增量），二次项使**中段每个 retry turn 是全任务里最贵的一批**。实测中位任务 26 turn、最重 112 turn，go 重试是主要贡献者之一。

根因假设（执行时先核实）：`go --step` 缺少"发起的是前序已完成/唯一确定的下一步时就自愈对齐"的能力，且失败消息未直接回送当前唯一合法可 `go` 的 step id，导致 Agent 必须额外一轮才能拿到答案。

## 验收

- [ ] `go --step` 因顺序不匹配失败时，错误输出必须**直接给出当前唯一合法可执行的 step id 及可复制的 `docpath go --step <id>` 命令**，使 Agent 无需再调 `next`/读 `current.md` 即可纠正（把 2–3 turn 压成 1 turn）。
- [ ] 当发起的步骤是"其前序步骤均已完成的唯一下一步"时，评估自动对齐到合法步骤或直接放行，消除本可避免的失败。
- [ ] 目标：`go` 失败率从实测 33% 降至 **<10%**；重任务（>40 turn）由 go 重试产生的 turn 数下降过半（用 trace 复核）。
- [ ] 为"顺序不匹配失败"补测试，断言输出含可复制的正确 `go --step` 命令。
- [ ] 全量测试与 typecheck 通过，零行为回归；不削弱非法跳步的拦截能力。
