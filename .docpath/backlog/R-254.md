## 背景
[来源: docpath 项目现场，R-251 修复过程中复现] 执行 `docpath review --skip-skill-review docpath-review-javascript --reason "..." --skip-skill-review docpath-review-typescript --reason "..."`（同一 skill gate 传了两次 `--skip-skill-review`）时，review 崩溃并输出：
`❌ 未预期的错误 / item.split is not a function`
被顶层 catch 吞成笼统的"未预期的错误"，无堆栈（需 DOCPATH_DEBUG=1 才看得到）。

## 代码核实 (2026-07-06)
- `src/commands/review.ts:355-358` `normalizeSkillSkipList`:
  `return input.flatMap((item) => item.split(',')).map((item) => item.trim()).filter(Boolean);`
- 假设 `input` 的每个 item 都是 string。但当 CLI 把 `--skip-skill-review A --skip-skill-review B` 重复 flag 收集时，或 `--skip-skill-review` 未带值时，item 可能是 `undefined`/`true`/对象，`item.split(',')` 直接 TypeError。
- 异常被 `src/index.ts:169` 顶层 catch 吞成"未预期的错误"（R-248 同款顶层 catch 问题在 review 路径复现）。
- 用逗号分隔单次传参 `--skip-skill-review A,B --reason "..."` 可绕过，行为正常。

## 验收
- `normalizeSkillSkipList` 对非 string item 做防御（`String(item)` 或过滤），或用 `Array.isArray` 校验。
- CLI 层对 `--skip-skill-review` 重复 flag / 缺值给出明确错误（"skill 名不能为空"），而非 crash。
- 顶层 catch（R-248 范畴）对这类参数错误应给出具体错误信息，而非"未预期的错误"。
- 回归: 重复传 `--skip-skill-review` 不再 crash，给出可操作错误或正确归并。

## 复现证据补充 (2026-07-13, docpath 项目现场)

除上文 skip-skill-review 解析 crash 外，review 的 scope 推导在
`--scope last_commit` 支路另有一支 bug，现场实测：

- 命令: `docpath review --dry-run --scope last_commit`
- 输出: `fatal: invalid --pretty format: ""` → 随后判 `未发现变更文件` 并退出。
- 根因推断: scope=last_commit 派生 `git log` 等命令时某一处把空字符串作为
  `--pretty` 值传入，git 拒绝并 fatal；上游未捕获该 fatal，将其当作"无变更"。
- 影响: agent 想只审最近一次单次 commit 的变更集时无法生效，被迫退用
  `--scope all`/task 累积 diff；后者会把多个 task 周期的改动混审，触发
  file-set mismatch（R-255 范畴）误拦。
- 与 R-255 关系: 本支 bug 是 R-255 file-set mismatch 误拦的结构性诱因之一
  —— agent 缺可用 last_commit scope，被迫混审。修本条有助于从源头降低
  R-255 的触发频率，但不替代 R-255 自身的"证据元数据问题与代码缺陷降级"。

### 追加验收（针对 last_commit 支路）
- `review --scope last_commit [--dry-run]` 不再 fatal，能正确解析最近单次
  commit 的变更文件集并纳入审查。
- 空 `--pretty` 等派生 git 参数需在调用层做非空校验/默认值，而非让 git 拒绝。
