## 背景
[来源: codex session 挖掘 @ evoucher 2026-07] 原始描述：`docpath go --step` 与 `docpath backlog promote` 在 worktree 有未提交变更时一律拒绝，未区分 DocPath 自身产物与业务代码变更，导致 agent 每完成一步想推进时被拦。证据: session 行 732、854、1310、1470、2154 共 5 次 dirty worktree 拒绝。

## 代码核实 (2026-07-06，结论：代码层"未区分产物"已修复，本条重定位)
- `src/utils/git-dirty-guard.ts` 已区分 `docpathFiles` vs `nonDocPathFiles`：
  - `assertNoNonDocPathChangesForExecutionStart` (line 142): `go` 命令用此，已放行所有 `.docpath/` 产物，仅当存在**非 DocPath 业务变更**时拒绝。
  - `assertCleanWorktreeForNewTask` (line 132): `promote` 调用时传 `allowDirtyPath: isPromoteBacklogEvidencePath`，放行 promote 自身 evidence 路径。
- 错误信息 (`buildDirtyWorktreeError` line 64) 已含 `changed_files` 列表 + `docpath changes --agent` 收口提示 + `docpath worktree create` 并行提示。
- session 里的 5 次拒绝是 evoucher 真实存在未提交业务变更（非 DocPath），guard 行为**正确**，并非"未区分产物"。
- 真正痛点: codex agent 反复触发被拒，是因为它没有在被拒后执行 `docpath changes --agent` + commit 收口，而是反复重试 go/promote。这是 agent 侧流程教育问题，不是 guard bug。

## 重定位
本条不再视为 guard 代码缺陷。建议:
1. 降级为 P3 或 dropped（guard 行为已正确且提示充分）。
2. 或转向 agent 侧: 在 evoucher 的 codex AGENTS.md / CLAUDE.md 里补约定——遇到 dirty worktree 拒绝时，必须先跑 `docpath changes --agent` 收口并 commit，不得直接重试 go/promote。
