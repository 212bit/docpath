# Support brand-new project intake workflow from source documents

## 背景

DocPath currently models backlog entries well for incremental work inside an existing developed project. That flow is too narrow for a brand-new project where the starting point may be a PPT deck, API documentation, introductory documents, meeting notes, or a single rough requirements document.

The missing capability is an upstream project-intake workflow that converts raw source materials into a project brief, PRD/spec, architecture brief, milestone plan, and then actionable backlog items.

## Requirements Analysis

### Goal

Add a first-class DocPath workflow for new-project intake before normal backlog/spec/plan execution.

### Actors

- User or product owner who has raw project materials but not a shaped backlog.
- Agent that must analyze source materials without prematurely implementing.
- Engineering/product/design reviewers who need explicit assumptions, risks, and open questions before project execution.

### Source Inputs

- PPT or slide-derived text.
- API/interface documents.
- Introductory or background documents.
- Single requirements document.
- Meeting notes or mixed source notes.

### Functional Requirements

- Support an intake entry point for raw project materials.
- Preserve the existing backlog flow for small incremental work.
- Separate raw material capture from synthesis, project brief, PRD/spec, architecture brief, planning, and backlog generation.
- Require Decision Brief evidence because this changes workflow and agent behavior.
- Require explicit user confirmation before promotion or implementation.
- Make the output auditable through DocPath artifacts and CLI summaries.

### Non-Goals

- Do not replace the existing backlog mechanism.
- Do not auto-promote raw project materials into implementation tasks.
- Do not depend on external LLM calls or network services for deterministic workflow state.
- Do not require every new project to have all document types; a single source document must be enough to start.

## Product Analysis

### User Value

Users can start from incomplete project material and still get a structured path toward execution. This reduces the gap between "I have documents" and "I have a scoped, reviewable project plan."

### Core Journey

1. User creates a new project-intake item from one or more source documents.
2. DocPath records source inventory and extraction assumptions.
3. Agent synthesizes goals, users, scope, dependencies, risks, and open questions.
4. User reviews a project brief and confirms direction.
5. DocPath generates or accepts PRD/spec and architecture brief evidence.
6. DocPath creates milestones and backlog items only after confirmation.

### Success Criteria

- A user can start a new project without first inventing backlog-sized tasks.
- The workflow distinguishes raw source material from confirmed implementation scope.
- Existing backlog commands remain compatible for incremental project work.
- Quality gates make it clear when implementation is blocked by missing product, technical, or decision evidence.

## UI/UX Analysis

This is primarily a CLI and artifact workflow. If surfaced in a UI later, the information architecture should expose:

- Source materials inventory.
- Synthesis summary.
- Project brief.
- Open questions and assumptions.
- Decision Brief.
- PRD/spec status.
- Architecture brief status.
- Milestone/backlog generation status.

Required states:

- Empty state: no source materials captured.
- Partial state: materials captured but not synthesized.
- Review state: brief/spec/architecture needs user confirmation.
- Blocked state: missing required decision or source evidence.
- Ready state: project can be planned or decomposed into backlog items.

## Technical Analysis

### Workflow Model

Introduce a new upstream workflow concept, likely distinct from normal backlog items:

- `project-intake`: raw source capture and inventory.
- `project-synthesis`: structured analysis of raw materials.
- `project-brief`: product-level framing and boundaries.
- `project-spec`: PRD/spec evidence.
- `project-architecture`: architecture brief evidence when software delivery is expected.
- `project-plan`: milestones and executable work decomposition.
- `backlog-generation`: optional generation of normal backlog items after confirmation.

### Compatibility

Existing backlog behavior must remain unchanged for incremental tasks. Backlog should continue to be appropriate for small scoped changes inside known projects.

### CLI Considerations

Potential commands or routes to evaluate during spec:

- `docpath project capture`
- `docpath project analyze`
- `docpath project brief`
- `docpath project plan`
- `docpath project backlog`

Alternative: extend `docpath backlog capture` with a project-level profile. This is less clean because it risks overloading backlog semantics.

### Test Strategy

- Unit tests for state transitions and readiness gates.
- CLI tests for capture/analyze/brief/plan routes.
- Regression tests proving existing backlog behavior is unchanged.
- Fixture tests for single-document and multi-document intake.
- Negative tests for auto-promotion prevention.

## Risks

### Product Risk

The workflow may become too heavy if it requires excessive ceremony for small projects. Mitigation: keep backlog/quick paths unchanged and make project-intake explicitly opt-in.

### Workflow Risk

Overloading backlog with project-level semantics would blur task granularity. Mitigation: prefer a distinct project-intake concept or explicit project profile.

### Technical Risk

Adding new workflow states may affect routing, `next`, `status`, `check`, and closeout logic. Mitigation: require compatibility tests around existing commands.

### Maintenance Risk

New artifacts increase long-term documentation and migration burden. Mitigation: define minimal required artifacts and avoid duplicating spec/plan responsibilities.

## Open Questions

### Blocking Before Implementation

- Should project-intake be a new top-level command namespace or an extension of backlog capture?
- What is the canonical artifact root for new project materials and generated briefs?
- Should DocPath ingest binary PPT/PDF files directly, or require extracted text/markdown first?
- What exact readiness gates are required before converting project-intake output into backlog items?

### Non-Blocking For Initial Spec

- Whether UI support is needed in the first version.
- Whether templates should be customizable per organization.
- Whether source document provenance should include hashes or only paths/references.

## Decision Brief

### Current Problem

DocPath lacks a strong path for brand-new projects that start from raw source documents instead of scoped backlog items.

### Goal

Create an upstream project-intake workflow that turns raw project materials into confirmed project artifacts and then backlog items.

### Options

- Option A: Keep using backlog for everything.
- Option B: Extend backlog with a project profile.
- Option C: Add a distinct project-intake workflow that can later generate backlog items.

### Recommended Option

Option C.

### Rationale

Brand-new project discovery has different semantics from incremental backlog work. A separate workflow keeps granularity clear, avoids breaking existing backlog behavior, and gives agents a safer route for analysis before implementation.

### Out Of Scope

- Direct implementation before spec approval.
- Auto-promoting generated backlog items.
- Replacing existing quick/backlog flows.

### Rollback

If the project-intake model proves too heavy, keep existing backlog behavior untouched and remove or hide the new project-intake route without changing backlog semantics.
