# Skill: Milestone & Backlog 智能规划与切片指南 (Milestone Planner)

> 核心目标：指导 Agent 在面对大目标/复杂特性时，遵循**垂直业务切片（Vertical Slice）**原则，将技术步骤正确沉降至 Task Steps，保持 Backlog 独立可验证与适度粒度。

---

## 1. 三层架构映射标准

```text
┌─────────────────────────────────────────────────────────────┐
│ 1. Milestone (M-###): 宏观业务目标 / 阶段性交付版本           │
│    - 包含 3 ~ 7 个 Backlog，聚合整体交付成果与验收标准 (DoD)   │
└──────────────────────────────┬──────────────────────────────┘
                               │ 垂直业务切片 (Vertical Slice)
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 2. Backlog (R-###): 独立可交付、可单独验证的业务功能单元     │
│    - 预计代码改动 80 ~ 300 行，可独立编写并运行业务单测       │
└──────────────────────────────┬──────────────────────────────┘
                               │ 技术实现动作分解
                               ▼
┌─────────────────────────────────────────────────────────────┐
│ 3. Task Steps (S1..Sn): 具体的代码与配置执行步骤             │
│    - DDL 建表、Mapper XML、DTO、配置注册等纯技术细节下沉此处 │
└─────────────────────────────────────────────────────────────┘
```

---

## 2. 垂直切片黄金法则 (Vertical Slice Principle)

- ❌ **禁止水平技术切片 (No Horizontal Slicing)**：
  严禁将“建表 (DBA)”、“写 Mapper (DAO)”、“写 DTO (Model)”、“写 SOFA/Spring XML (Config)”分别拆成独立 Backlog。
  水平切片的 Backlog 无法单独进行端到端测试，且会导致多次重复的 Task 生命周期（`spec` -> `plan` -> `check` -> `review` -> `journal` -> `commit`），造成巨大的管理与上下文浪费。
- ✅ **坚持垂直业务切片 (Vertical Slice)**：
  每个 Backlog 必须贯穿必要的各层（数据层 + 逻辑层 + 契约层），交付一个**完整且可验证的业务功能单元**。

---

## 3. 粒度红线与自检清单 (Granularity Gate)

在创建或拆解 Backlog 前，必须通过以下 3 项自检：

- [ ] **1. 独立可测性 (Verifiability)**：
  该 Backlog 完成后，是否能够编写并运行一组独立的业务单元测试或 API 调用进行闭环验证？
  *(若不能单独测试，说明它只是一个 Task Step，必须合并进相关业务特性)*
- [ ] **2. 命名与语义纯度 (Semantic Wholeness)**：
  Backlog 标题是否体现了**业务能力**而非单纯技术文件？
  *(❌ 反模式标题：`新建表结构`、`编写Mapper XML`、`配置XML注册`；✅ 标准标题：`采购申请数据持久层与契约定义`)*
- [ ] **3. 容量与数量控制 (Budget & Count Control)**：
  - 单个 Milestone 下拆出的 Backlog 数量建议在 **3 ~ 6 个**（若超过 8 个，必须检查是否存在微型碎片）。
  - 单个 Backlog 的预估代码变更量宜在 **80 ~ 300 行** 之间。

## 4. 常见反模式与重构范例 (Anti-Patterns vs Refactoring)

### 范例 1：数据持久层与接口契约
- ❌ **反模式（4 个微型 Backlog，流程空转 4 次）**：
  - `R-001`: 采购申请业务建表 (SQL)
  - `R-002`: 配套 Mapper 接口与 MyBatis XML
  - `R-003`: Facade SVC 契约与 DTO 定义
  - `R-004`: SOFA 配置文件注册
- ✅ **标准重构（1 个业务 Backlog，内含 3 个 Task Steps）**：
  - `R-001`: **采购申请数据持久层与 Facade 契约定义**
    - `S1`: DDL 建表 SQL 与 DTO 契约定义
    - `S2`: MyBatis Mapper 接口与 XML 映射
    - `S3`: SOFA 服务注册与持久层单测验证

### 范例 2：审批流与流程节点
- ❌ **反模式（8 个微型 Backlog，每个节点独立一条）**：
  - `R-010` 录入节点, `R-011` 供应商核查节点, `R-012` 需求审核节点, `R-013` 外发审批节点...
- ✅ **标准重构（按主干业务流聚合为 2~3 个 Backlog）**：
  - `R-010`: **采购申请录入与金额分流路由**（包含录入、核查、小额/集中终态归档）
  - `R-011`: **分散采购评审与外发审批流**（包含外发审批、抽签接入、结果全员评审）
  - `R-012`: **单一来源审批与移动端接入**（包含分管行领导审批、移动端接口）

---

## 5. 治理与重构命令指引

- **巡检碎片**：运行 `docpath backlog groom` 扫描是否存在同 Milestone 下的微型技术切片。
- **一键合并**：运行 `docpath backlog merge <source_ids...> --target <target_id>` 快速合并过细的 Backlog。
